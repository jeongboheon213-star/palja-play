# 최초 제공·복구·취소 구현 안내

상태: 코드·로컬 검증 및 실제 Supabase 구조/권한 적용 확인 완료. Vercel Preview TEST 연결과 실제 결제/열람/취소 검증 대기. 법률 최종 문구는 미검토다.

## 사용자가 보게 되는 흐름

결제 승인 → 구매 코드와 미열람 안내 → **리포트 열기** 또는 **아직 열지 않은 구매 취소**. 결제 성공 주소에 도착하거나 서버 승인을 받는 것만으로 본문 요청·열람 기록을 하지 않는다. 승인 결과가 불확실하면 결제 확인 화면에서 재시도하고 열람 버튼을 제공하지 않는다.

열기: 구매 코드·상품·같은 Signal·PAID·TEST/LIVE 환경을 확인하고, 리포트를 구성한 후 DB 함수가 주문 행을 잠가 다시 확인한다. DB `now()`로 최초 제공 시각을 기록하고 본문을 반환한다. 이후 열람은 처음 시각을 유지한다. DB 기록 실패는 본문을 반환하지 않는다.

서버 기록과 네트워크 전송 완료를 하나의 거래로 묶을 수는 없다. 기록 후 연결이 끊기면 사용자에게 본문이 도착하지 않았을 수 있으므로 콘텐츠 미제공 예외 지원이 필요하다. 이 기록은 서버의 제공 시작 기록이며 실제 독서 완료를 입증하지 않는다.

미열람 취소: 코드·상품·같은 Signal을 재확인한 DB 함수가 `content_opened_at IS NULL`일 때만 `REFUND_REQUESTED`로 잠근다. 리포트 열기와 취소가 동시에 성공할 수 없다. Toss 전체 취소 결과를 확인하고 `REFUNDED`를 기록한다. 네트워크·DB 실패로 결과가 불확실하면 `REFUND_REQUESTED`를 유지해 본문을 막고, 같은 멱등키로 재시도한다. 부분 취소를 전체 환불 성공으로 취급하지 않는다.

열람한 고객의 중복 결제·오류·콘텐츠 미제공·서비스 문제·표시/계약과 다른 제공·법령상 필요한 환불은 관리자 `refundOrder` 경로로 검토할 수 있다. 3분 마감이나 모든 환불의 일률 차단을 구현하지 않았다. 실제 고객 문의 연락처·응답 기한과 최종 정책은 LIVE 전 결정해야 한다.

## 구매코드 요청 제한

본문·미열람 취소 API에 같은 DB 제한을 적용한다. 10분 고정 구간에서 네트워크 범위당 30회, 코드당 15회, 서비스 전체 1,000회다. 성공 요청도 포함한다. DB 원자적 증가가 여러 Vercel 서버의 요청을 합산하며, DB/RPC가 없거나 응답이 잘못되면 503으로 닫는다. 제한 시 429와 `Retry-After: 600`을 반환한다. 인메모리 우회 대체는 없다.

Vercel 환경에서만 Vercel의 `x-vercel-forwarded-for`를 신뢰하며, 그 외 환경·누락·유효하지 않은 IP는 공동 미확인 버킷을 쓴다. IPv6는 /64로 묶는다. 헤더 동작 근거: [Vercel 공식 Request headers](https://vercel.com/docs/headers/request-headers). 별도 프록시를 추가하면 헤더 신뢰를 다시 검토해야 한다.

원 IP·구매코드는 DB 제한 테이블에 저장하지 않는다. 서버 키와 목적을 구분한 HMAC으로 해시한다. 익명화가 아니라 단기 가명 처리이며 LIVE 개인정보 안내에 반영해야 한다. 전화번호·이메일 등 새 입력은 요구하지 않는다. 다음 요청 시 20분 전 구간보다 오래된 행을 지운다(통상 약 20~30분 이내 기록). 요청이 없으면 만료 행이 물리적으로 남으므로 정기 삭제 작업은 LIVE 운영 검토 항목이다. 키 회전은 해당 버킷 식별자를 바꾼다.

공유 네트워크에서는 제한을 함께 받을 수 있으며, 분산 공격으로 전체 제한이 차면 정상 사용자도 잠시 막힐 수 있다. 초기 보수적 방어다. LIVE 전 트래픽 관찰·Vercel 방화벽 운영·보관 정책 검토가 필요하다.

## 관리자 도구

`scripts/payment-admin.ts`는 로컬에서 서버 환경 변수를 읽고 **TEST 주문만** 처리한다. 웹 관리자 API나 브라우저에 관리자 권한을 공개하지 않는다. Secret Key는 채팅·코드·GitHub·로그에 넣지 않는다. 실제 도구의 Toss 호출은 아직 미실행이다.

- `npx tsx scripts/payment-admin.ts refund ORDER_ID "중복 결제 확인"`: 열람 여부와 관계없이 사유를 기록한 TEST 예외 환불
- `npx tsx scripts/payment-admin.ts rotate-code ORDER_ID`: 영수증·주문 소유자를 확인한 뒤 PAID 주문의 코드 재발급. 기존 코드는 즉시 무효이고 최초 제공 시각은 유지한다.

도구는 자동으로 고객에게 메시지를 보내지 않는다. 본인 확인 없이 새 코드를 전달하면 구매 권한이 유출된다. 사업자 문의 경로와 LIVE 운영 도구는 별도 준비한다.

## DB 적용

2026-10-05 사용자 실행과 확인 JSON 13개로 실제 프로젝트의 구조/권한 적용을 확인했다. 아래는 적용 기록이며 재실행할 필요가 없다. 실제 앱의 열람·취소·제한 동작 검증은 Preview TEST 연결 후 진행한다.

이미 완료된 orders 권한 보정은 다시 요청하지 않는다. 필요한 신규 변경만 적용한다:

1. `20261005030000_orders_content_access.sql`
2. `20261005040000_content_access_and_limits.sql`

두 파일은 `supabase/phase2-apply.sql`에 실행 순서대로 합쳤다. 사용자가 기존 프로젝트의 SQL Editor에서 실행한다. 기존 주문 데이터 삭제·금액 변경은 없으며 짧은 스키마 잠금이 필요하다. 함수 실행권은 service_role만 받고 제한 테이블에는 service_role도 직접 접근권이 없다. 실패 시 단일 트랜잭션이 롤백한다. 적용 전에는 결제 OFF를 유지하며, Preview TEST 키 연결은 SQL 검증 이후에 한다.
